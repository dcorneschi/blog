Terraform Lock File Checksums: what zh: and h1: actually are

Title for the X editor (copy it into the title field).

Open any .terraform.lock.hcl and you'll see one h1: hash and a dozen zh: hashes per provider. Most people never look at them until terraform init fails with a checksum mismatch. Here is what they are, how to reproduce them by hand, and how to stop them from breaking CI.

Two hashes, two schemes

  • zh: is a plain SHA256 of the provider zip for one OS/architecture. It is the legacy scheme and only works for zips downloaded from the registry.
  • h1: is a dirhash of the files inside the provider: the same algorithm Go uses for go.sum. It works no matter how the provider was delivered.

Both are platform-specific: linux_amd64 and darwin_arm64 builds of the same version have different hashes.

Reproduce h1: in one line

Inside the unpacked provider directory (bpg/proxmox 0.116.0, linux_amd64):

sha256sum $(ls | LC_ALL=C sort) | sha256sum | awk '{print $1}' \
  | xxd -r -p | base64
# 6E3NlPgUs+EPAeL/XcsjTRXqQH1kwTmaW8wI8kdv7LM=

That is exactly the h1:6E3NlPgUs+EPAeL/XcsjTRXqQH1kwTmaW8wI8kdv7LM= in the lock file. The recipe: SHA256 every file, write <hash> <name> lines sorted by name, SHA256 that list, Base64 the binary result. Permissions and timestamps don't count.

Reproduce zh: with sha256sum

sha256sum terraform-provider-proxmox_0.116.0_linux_amd64.zip
# 9c83aa1ed438e0f4337bd4e05b35df55292f34d6b70aab906506e1594920811d

Same value as zh:9c83aa1e… in the lock file, and the same line as in the provider's signed SHA256SUMS file.

Why 14 zh: but only one h1:?

The zh: list is copied from SHA256SUMS, which covers every platform the provider is built for: 13 zips plus the manifest.json, which isn't a provider at all. The h1: is computed locally, so you only get it for the platform you ran terraform init on.

Terraform needs just one match

When it verifies a provider, Terraform accepts it if any single hash in the lock file matches. Then it adds the hashes it can vouch for. Two consequences:

  • A lock file with only h1: for your platform is fine: terraform init adds all the zh: back.
  • An attacker who adds one extra h1: for a tampered binary breaks nobody else. Review lock file diffs: every zh: should appear in the provider's signed SHA256SUMS.

The classic error: macOS laptop, Linux CI

The lock was created on a Mac and CI on Linux fails with "doesn't match any of the checksums previously recorded in the dependency lock file". The hash type doesn't matter, the platform does. Record every platform you use:

terraform providers lock \
  -platform=linux_amd64 \
  -platform=darwin_arm64 \
  -platform=darwin_amd64

Commit the result. It doesn't need a prior terraform init.

Lock it down in CI

terraform init -lockfile=readonly

Terraform still verifies checksums but fails instead of rewriting the lock file, so lock changes only arrive through a reviewed commit.

Three things that surprise people

  • Mirrors give you only h1:. A lock created from terraform providers mirror has no signed SHA256SUMS, so it gets h1: for the current platform only, and Terraform warns "Incomplete lock file information".
  • terraform init -upgrade drops the other platforms. After an upgrade only your own h1: is left. Run terraform providers lock -platform=… again.
  • The first init is trust-on-first-use. Hashes protect you from tampering after the lock exists. Create it in a trusted environment and commit it.
